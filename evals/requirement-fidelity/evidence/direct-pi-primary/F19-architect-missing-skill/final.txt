HOLD: I can’t produce a confident storage/network architecture because **payload size and retention are load-bearing facts** for SCALE-1.

Known binding drivers:
- **SCALE-1:** 1000× current 100 req/s = **100,000 req/s**
- **AVAIL-1:** **99.99% availability**
- Unknown but dominant:
  - payload size distribution: p50/p95/p99/max
  - retention period
  - read/write ratio
  - replay/export requirements
  - consistency and loss tolerance

Conditional boundary:

- If payloads are small, e.g. metadata/event-sized, and retention is short, a horizontally scaled stateless API tier + partitioned durable log + replicated database/object storage can plausibly meet 100k req/s and 99.99%.
- If payloads are large or retained long-term, the dominant design becomes object-storage-first ingestion with metadata indexing, async processing, lifecycle policies, and bandwidth-aware regional partitioning.
- If payloads are unbounded, synchronous request handling should reject or redirect large bodies to pre-signed object uploads; otherwise availability and latency will be hostage to network/storage variance.

Recommended structure until those facts are known:

```mermaid
flowchart LR
  C[Clients] -->|requests| LB[Global/Regional Load Balancer]
  LB -->|routes traffic| API[Stateless API Service]
  API -->|small metadata writes| DB[(Partitioned Metadata Store)]
  API -->|large payloads| OBJ[(Object Storage)]
  API -->|append events| LOG[(Durable Partitioned Log)]
  LOG -->|async processing| W[Workers]
  W -->|updates status/indexes| DB
  API -->|metrics/traces/errors| OBS[Observability]
```

Recommendation: use a **stateless API + partitioned durable log + object storage for payloads + metadata store**. This keeps the service viable across unknown payload sizes without committing all traffic to the database.

Flip condition:
- If confirmed payloads are tiny and retention is short, simplify to API + partitioned database/log.
- If payloads are large or retained for months/years, make object storage the source of truth and keep databases metadata-only.

One-way doors:
- Public API payload semantics: hard to change later. Prefer upload indirection for large bodies from day one.
- Retention guarantees: do not promise until storage cost and lifecycle policy are known.
- Data deletion/compliance behavior: must be designed before retention is finalized.
