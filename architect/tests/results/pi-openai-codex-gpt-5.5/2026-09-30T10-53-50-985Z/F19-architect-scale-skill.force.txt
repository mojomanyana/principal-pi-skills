## Design note: queue-backed admission service boundaries

Drivers: SCALE-1: 100 req/s now, must tolerate 100,000 req/s, 1 KiB payloads, 24-hour replay retention. AVAIL-1: 99.99% monthly availability.  
Constraint: do **not** quietly design for 10x; the binding requirement is 1000x until formally changed.  
Preference: low cost.  
Evidence gap: no benchmarks have run, so capacity numbers are sizing assumptions, not proof.

## Scale implications

At 100,000 req/s × 1 KiB:

- Ingress payload only: ~100 MiB/s before protocol, metadata, replication, indexing, TLS overhead.
- 24-hour raw retention: ~8.6 TiB/day before replication.
- With 3x replication and overhead, storage can plausibly land in the tens of TiB/day range.
- 99.99% monthly availability allows roughly 4.4 minutes downtime/month.

That scale is not compatible with a single database table or small broker unless the 1000x driver is relaxed.

## Component boundaries

Recommended boundary split:

1. **Admission API**
   - Synchronous HTTP/gRPC ingress.
   - Performs authentication, schema validation, request size limits, idempotency-key checks, and cheap admission decisions.
   - Does **not** perform downstream business processing.
   - Returns accepted/rejected quickly.

2. **Admission Log / Queue**
   - Durable append-only buffer with 24-hour replay.
   - Partitioned by a stable routing key.
   - Replicated across availability zones.
   - Source of truth for accepted admission events.

3. **Admission Metadata Store**
   - Stores idempotency records, request status pointers, tenant quotas, and lightweight indexes.
   - Not the primary payload store.
   - Must be sharded or partitioned if idempotency is checked at 100k req/s.

4. **Consumers / Processing Workers**
   - Consume from the queue independently.
   - Horizontally scalable.
   - Own business-side retries, dead-lettering, and poison-message handling.

5. **Replay / Audit Interface**
   - Reads retained queue data for 24 hours.
   - Used for recovery, reprocessing, and incident investigation.
   - Should not share the hot admission path.

6. **Control Plane**
   - Manages tenant limits, partition configuration, schema versions, rollout flags, and operational policy.
   - Lower QPS than the data plane.

    Client[Clients] -->|submit 1 KiB request| API[Admission API]

    Control -->|partition and retention policy| Queue

## Options

### 1. Boring option: API + Postgres table as queue

Use the database as the admission queue with polling consumers.

- Meets current 100 req/s: likely yes.
- Meets 100,000 req/s with 24h replay: unlikely without heavy sharding and operational risk.
- Meets 99.99%: possible only with mature HA setup, but write pressure and replay contention are major risks.
- Cost: low initially, but risks expensive failure at SCALE-1.

Verdict: acceptable only if the official target is changed away from 1000x.

### 2. Managed partitioned log: API + Kafka/Pulsar/Kinesis/Event Hubs equivalent

Use a durable partitioned log as the acceptance boundary.

- Meets 100,000 req/s: plausible with enough partitions, provisioned throughput, and benchmarked producer settings.
- Meets 24-hour replay: native fit.
- Meets 99.99%: plausible with managed multi-AZ service or carefully operated cluster.
- Cost: higher than the boring option, but directly aligned with the retention and replay driver.

Verdict: best fit for the stated drivers.

### 3. API + object storage batches + notification queue

Admission API batches payloads into object storage and publishes batch pointers to a smaller queue.

- Meets storage cost preference: strong.
- Meets 24-hour replay: yes, if object retention and manifests are correct.
- Meets low-latency admission: maybe, but batching introduces complexity and flush/failure edge cases.
- Meets 100,000 req/s: plausible, but more custom correctness work.
- Operational complexity: higher.

Verdict: consider if cost dominates and slightly more complex replay semantics are acceptable.

## Recommendation

Choose **Option 2: Admission API backed by a managed partitioned durable log**.

Reason: the binding requirements are high-throughput append, 24-hour replay, and 99.99% availability. A real log/queue system is the boring scalable primitive for that workload.

Do **not** silently design for 10x. If the organization wants a 10x design, record a formal requirement change from 100,000 req/s to 1,000 req/s, with the owner accepting that SCALE-1 is no longer met.

Flip condition:

- Use the database-backed queue only if the binding target is formally reduced below roughly the range where the DB queue can be benchmarked with headroom.
- Consider object-storage batching if queue-retention cost dominates and replay can tolerate batch-level semantics.

## Main risks

- **Under-partitioning:** not enough partitions to absorb 100k req/s or consumer lag.
- **Hot keys:** tenant or routing-key skew can overload individual partitions.
- **Idempotency bottleneck:** a centralized idempotency store can become the true limiter.
- **Replay interference:** audit/replay reads must not starve the hot consumer path.
- **Retention cost:** 24-hour retention at 100k req/s is multi-TiB/day before replication.
- **Availability mismatch:** 99.99% requires multi-AZ design and careful dependency budgeting.
- **False confidence:** no benchmarks have run, so all sizing must be validated before treating this as proven.

## One-way doors

- Queue technology choice: high migration cost once producers, consumers, replay, and ops depend on it. Rollback requires dual-writing or bridge consumers.
- Public admission API contract: hard to change after clients integrate. Use explicit schema versions.
- Partition-key strategy: painful to change after data and consumers depend on ordering semantics. Prefer documenting ordering guarantees narrowly.

## Validation / observability

Needed before claiming SCALE-1 is met:

- Producer throughput at 100k req/s with p95/p99 admission latency.
- Queue append error rate and broker throttling.
- Consumer lag by partition.
- Hot-partition detection.
- Idempotency-store read/write latency.
- Replay throughput without harming live processing.
- Availability dependency budget for API, queue, metadata store, and auth.
