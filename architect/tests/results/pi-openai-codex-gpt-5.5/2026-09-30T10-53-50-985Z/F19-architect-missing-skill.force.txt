## Design note: service structure for SCALE-1 / AVAIL-1

Drivers:  
- SCALE-1: 1000× current 100 req/s = **100,000 req/s**.  
- AVAIL-1: **99.99% availability**.  
- HOLD: payload size and retention are unknown, and they dominate storage/network design.

Constraints:  
- No follow-up allowed.  
- Cannot invent payload/retention values because they are load-bearing for architecture sizing.

Recommendation: **HOLD on final architecture** until payload size distribution and retention/SLOs are known.

A safe conditional boundary:

```mermaid
flowchart LR
  Client[Clients]
  LB[Global / regional load balancer]
  API[Stateless API tier]
  Queue[Durable ingestion queue]
  Workers[Async workers]
  Store[(Primary storage)]
  Index[(Query/index store)]
  Obs[Metrics/logs/tracing]

  Client -->|HTTPS requests| LB
  LB -->|routes traffic| API
  API -->|validates + enqueues| Queue
  Queue -->|pulls work| Workers
  Workers -->|writes payload/metadata| Store
  Workers -->|updates searchable views| Index
  API -->|reads metadata/query results| Index
  API -->|fetches payloads when needed| Store
  API -->|emits signals| Obs
  Workers -->|emits signals| Obs
```

Use this structure only as a **shape**, not a final design:

- **Stateless API tier** horizontally scaled across at least 2–3 zones.
- **Durable queue** to absorb spikes and decouple request acceptance from storage writes.
- **Async workers** sized independently from request traffic.
- **Storage split** between payload/blob storage and query/index metadata if payloads are large or retained long-term.
- **Multi-AZ deployment** for 99.99%; consider multi-region only if zone/region failure recovery requirements demand it.

Flip conditions:

- If payloads are small and retention is short, a simpler Postgres-backed service may be enough.
- If payloads are large or retained long-term, use object/blob storage plus metadata DB.
- If synchronous durability is required at 100k req/s, queue/storage choice becomes the central design decision.
- If 99.99% must survive regional failure, move from multi-AZ to active-active or active-passive multi-region.

One-way doors: none yet — final storage, retention, and replication choices are deferred.
