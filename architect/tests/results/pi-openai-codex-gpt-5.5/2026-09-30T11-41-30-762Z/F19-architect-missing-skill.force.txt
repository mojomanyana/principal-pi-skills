## Design note: service structure for SCALE-1 / AVAIL-1

Drivers:  
- SCALE-1: 1000× current 100 rps = **100,000 requests/sec**
- AVAIL-1: **99.99% availability**
- HOLD: payload size and retention are unknown and explicitly dominate storage/network design, so storage tier, queue sizing, bandwidth, backup/restore, and cost cannot be finalized.

Constraints:  
- Cannot ask follow-ups.
- Must not invent load-bearing payload/retention numbers.

Options:

1. **Boring option: single-region stateless service + managed Postgres**
   - Meets: simplicity, fast delivery.
   - Misses: 99.99% under regional failure; likely misses 100k rps unless workload is mostly cached/read-only.
   - Use only if 100k rps is bursty, payloads are small, and downtime during regional incidents is acceptable.

2. **Recommended baseline: multi-AZ stateless service + managed regional datastore + async ingestion**
   - Components:
     - L7 load balancer
     - horizontally scaled stateless API workers
     - request validation/auth at edge
     - durable queue/log for writes or heavy work
     - worker fleet
     - managed multi-AZ database/object storage
     - Redis/cache only for derived/read-through data
   - Meets: 100k rps for stateless/API-heavy traffic; 99.99% for common AZ/node failures.
   - Misses: regional disaster recovery unless paired with warm standby.

3. **Higher-availability option: active-active or active-passive multi-region**
   - Meets: stronger availability if regional failure must be inside AVAIL-1.
   - Costs: data consistency complexity, conflict handling, higher ops burden, expensive cross-region replication.
   - Only justified if 99.99% includes regional outage survival.

Recommendation:  
Choose **Option 2** as the default structure, but make storage/network sizing a gated decision. Flip to **Option 3** if AVAIL-1 is defined to include regional failure or if measured regional failover RTO/RPO requirements cannot be met inside the 99.99% budget.

One-way doors:  
- Public API contracts: version from day one; rollback by serving old and new versions in parallel.
- Data model/storage choice: defer final choice until payload size, retention, query patterns, and RPO/RTO are known.

Validation/observability:  
- Load test to 100k rps with representative payloads before committing capacity.
- Track p50/p95/p99 latency, error rate, queue lag, saturation, DB IOPS, network egress, and regional/AZ failover behavior.

Decision record: not complete until payload size, retention, consistency needs, and regional failure scope are known. Any confident storage/network decision before that would be pretending away the dominant constraint.
