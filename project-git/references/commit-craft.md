# Commit Craft

This is where most of the difference between junior and senior git work shows up. The model already knows `git commit -m`. What separates good from bad is what's in that message and how the diff was shaped before it.

The four ideas below cover the craft:

1. **Atomicity** — one logical change per commit.
2. **Subject/body discipline** — subject says what, body says why.
3. **Splitting messy diffs** — `git add -p` is the workhorse.
4. **When to amend, when to commit anew** — and never on shared history.

---

## 1. Atomicity

A commit is *atomic* when it captures exactly one logical change, no more and no less. The test: could you bisect with `git bisect` to this commit and have it tell you something meaningful? Could you revert this commit cleanly without leaving the codebase in a broken state?

### Atomic — yes

```
feat(auth): add OAuth2 callback handler
```
Adds one route, one handler, one test. Reverting cleanly removes the OAuth flow without touching unrelated features.

### Atomic — no

```
feat: OAuth + fix login bug + update deps + rename utility module
```
Four logical changes. If the login fix turns out to break something, you cannot revert it without also undoing the OAuth work. Bisect will land here and tell you "something in this 800-line diff broke things." That is not useful.

### How to handle a sprawling working tree

If you find yourself with a working tree that contains multiple logical changes, do **not** mash them into one commit just because they happened in the same session. Split them with `git add -p` (see §3). The thirty seconds it takes to partition saves an hour for the future debugger.

If splitting is genuinely impossible (rare — usually a misjudgment), then at minimum write a body that itemizes the changes. The commit is still suboptimal, but at least it's documented.

## 2. Subject and body

The commit message is two parts: a subject (always required) and a body (often required, sometimes optional).

### Subject

- **Imperative mood.** "add OAuth handler" not "added OAuth handler" and not "adds OAuth handler". Read it as completing the sentence *"If applied, this commit will ___"*. This isn't pedantry; it matches the language git itself uses (`git revert`, `git cherry-pick`, generated merge messages).
- **Under 50 characters when possible, 72 absolute max.** `git log --oneline` truncates at terminal width; longer subjects get cut off mid-word.
- **Lowercase by default** (after the `type(scope):` prefix). `feat(auth): add OAuth callback`, not `feat(auth): Add OAuth Callback`.
- **No trailing period.** It's a title, not a sentence.
- **Type and scope** — see Conventional Commits below.

### Body

The body explains **why** the change was made. The diff already shows **what** — repeating that in prose is waste.

- **Blank line between subject and body.** Git tooling depends on this.
- **Wrapped at 72 columns.** `git log` shows it as a wall of text otherwise. Most editors can be configured to hard-wrap at 72 for git commit messages.
- **Reasoning, context, alternatives considered, consequences.** Not "this commit adds an OAuth handler" — the subject said that.
- **References to issues, ADRs, prior commits** belong here.

### Trailers (the footer)

After the body, separated by a blank line, structured trailers in `Key: Value` form. The well-known ones:

- `Refs: #123` — related but not closed by this commit
- `Fixes: #123` — closed by this commit (when merged via PR), but the convention is also widely used to indicate the commit fixes a regression introduced elsewhere
- `Closes: #123` — closes the issue (used in PR bodies more than commit messages, but valid both places)
- `Co-authored-by: Name <email>` — GitHub renders avatars from this
- `Signed-off-by: Name <email>` — DCO signoff (auto-generated by `git commit -s`)
- `Reviewed-by: Name <email>` — when applying patches from another author
- `Reported-by: Name <email>` — credit for finding a bug

### Worked example — strong commit message

```
feat(auth): add OAuth2 callback handler

The login flow needs a callback endpoint to receive the authorization code
from the IdP. Adds /auth/oauth/callback, exchanges the code for tokens via
the existing token-exchange service, and writes the session cookie.

Chose to keep state validation in-memory (cookie-signed nonce) rather than
in Redis because the auth domain doesn't yet justify a stateful dependency.
This is reversible — see ADR-0011 for the threshold at which we'd revisit.

Refs: #142
Fixes: #138
Co-authored-by: Pat Reviewer <pat@example.com>
```

Why this is strong:
- Subject is under 50 chars, imperative, scoped, lowercase.
- Body explains *why* the route exists and *why* state lives where it does.
- The alternative (Redis-backed state) is named and justified by deferral.
- Trailers carry both close-and-ref links and co-author credit.

### Worked example — weak commit message

```
fixed bug
```

Why this is weak:
- No subject discipline (not imperative, not scoped).
- No body — the *why* and the *what bug* are invisible.
- No links — a future bisect lands here with zero context.
- "fixed" is past tense, conflicting with git's own grammar.

## 3. Splitting messy diffs with `git add -p`

This is the single most underused command in everyday git. When your working tree contains multiple logical changes that you want as separate commits, `git add -p` walks you through each hunk and lets you stage selectively.

```bash
git add -p              # interactive hunk staging
```

Per-hunk options:
- `y` — stage this hunk
- `n` — don't stage this hunk
- `s` — split this hunk into smaller hunks (when git can)
- `e` — manually edit the hunk (advanced; for surgical staging)
- `q` — quit
- `?` — help

After the partition, `git diff --cached` shows what's staged, `git diff` shows what's not. Commit the staged set, then repeat for the next logical group.

### Companion commands

```bash
git diff --cached                       # what's staged
git diff                                # what's unstaged
git restore --staged <file>             # unstage a file (keep working tree changes)
git stash --keep-index                  # stash the unstaged stuff while you test the staged set
```

The `git stash --keep-index` trick is gold: stage what you want to commit, stash the rest, run tests against ONLY the staged set, then commit if green and `git stash pop` to bring back the rest.

## 4. Amend vs new commit

`git commit --amend` rewrites the last commit. It's the right tool when:

- You forgot to add a file to the last commit and that commit isn't pushed yet.
- The commit message has a typo or missing trailer (and isn't pushed yet).
- You realize you split a change badly and want to fold a small fixup in (alternative: use a `fixup!` commit and autosquash; see [rebase-and-merge.md](rebase-and-merge.md)).

```bash
# Amend the last commit, keeping its message
git commit --amend --no-edit

# Amend and edit the message
git commit --amend

# Amend without changing any files (just the message)
git commit --amend -m "feat(auth): add OAuth2 callback handler"
```

### When NOT to amend

- **After the commit is pushed to a shared branch.** Amending changes the SHA, which means anyone else who has pulled that commit has a divergent history. You'd need to force-push, which is destructive (see tenet 3 in SKILL.md and the policy in [safety-and-secrets.md](safety-and-secrets.md)).
- **When the change is large enough to be its own commit.** "Fixed the bug I introduced in the last commit" should usually be a new commit, not an amend. Bisect prefers granularity over neatness.

### Fixup commits — the right way to "amend a not-most-recent commit"

If you want to fold a fix into a commit that isn't the most recent one (but is on your local feature branch, not yet pushed), use a `fixup!` commit and autosquash:

```bash
# Make the fix, then:
git commit --fixup=<sha-of-target-commit>

# When ready to clean up before pushing:
git rebase -i --autosquash <base-branch>
```

Git will reorder the `fixup!` commit next to its target and mark it for squashing. You only have to confirm in the editor.

See [rebase-and-merge.md](rebase-and-merge.md) for full autosquash/fixup workflow.

## 5. Conventional Commits — the type/scope/description prefix

Conventional Commits ([conventionalcommits.org](https://www.conventionalcommits.org/)) is the prefix convention this skill defaults to. It's not the only valid style, but it's the one that automated tooling (semantic-release, conventional-changelog, git-cliff) expects, and it's worth adopting if the project doesn't already have a different convention.

Format:
```
<type>(<scope>): <description>

[optional body]

[optional trailers]
```

### Types

Pick the **dominant** type if the change spans multiple categories. If you can't pick a dominant type, the change is probably non-atomic and should be split.

- `feat` — new user-facing feature
- `fix` — bug fix
- `perf` — performance improvement (not refactor unless behavior changed)
- `refactor` — code change that doesn't change behavior
- `docs` — documentation only (including ADRs)
- `test` — adding or fixing tests
- `build` — build system, dependencies, packaging
- `ci` — CI/CD configuration (workflows, actions, pipelines)
- `chore` — maintenance work not covered above (dep bumps, cleanups)
- `style` — formatting, whitespace (rare; usually handled by formatters in `chore`)
- `revert` — reverts a previous commit (use `git revert` which prefills this)

### Scope

The scope is the area of the codebase affected. Inferred from the files changed. Conventions vary:

- Module/package name: `feat(auth):`, `fix(payments):`
- Component name: `feat(checkout-form):`, `fix(nav):`
- Layer: `refactor(db):`, `feat(api):`
- Feature flag: `feat(beta-search):`
- ADR or RFC number for docs: `docs(adr-0007):`, `docs(rfc-12):`

Scope is **optional**. Omit it (`feat: add OAuth login`) if the change is genuinely cross-cutting (rare for atomic commits) or if the project doesn't use scopes.

### Breaking changes

Two ways to mark a breaking change:

```
# Inline marker
feat(api)!: drop /v1/users (use /v2/users)

# Footer
feat(api): replace pagination scheme

BREAKING CHANGE: cursor-based pagination replaces offset pagination on
all /v2 endpoints. Callers must update to the new `cursor` query param.
```

Both are valid; the inline `!` is harder to miss; the footer body is more discoverable in tools like git-cliff.

### Examples (good)

```
feat(auth): add OAuth2 callback handler
fix(payments): handle null response from Stripe webhook
docs(adr-0007): record decision to migrate Postgres → CockroachDB
refactor(db): extract connection pooling into separate module
perf(search): use trigram index for fuzzy match (50ms → 5ms p99)
build(deps): bump typescript 5.3 → 5.4
ci(release): add provenance attestation to npm publish
chore(release): v1.2.0
revert: feat(auth): add OAuth2 callback handler
```

### Examples (bad — and why)

```
update stuff                                       # no type, no scope, no information
WIP                                                # never push a WIP message; squash it before pushing
feat: stuff                                        # type without information
feat(auth): Added OAuth callback handler.          # past tense, capitalized, trailing period
fix and refactor                                   # two types — split or pick dominant
🚀 ship it!!!                                      # emoji are fine if the project uses them, but the message has no information
```

## 6. Quick reference — the checklist before `git commit`

Before running `git commit`, mentally walk this:

1. Is the staged diff one logical change? If not, `git reset` and re-stage with `add -p`.
2. Is the subject under 50 chars, imperative, lowercase, with type and (if used) scope?
3. Does the body explain *why*, not *what*?
4. Are issue references in the trailers (`Refs:`, `Fixes:`, `Closes:`)?
5. Co-authors and DCO signoff present if applicable?
6. Is anything in the staged diff a secret, .env, key, or token? (See [safety-and-secrets.md](safety-and-secrets.md).)
7. Is this commit going to a branch where amend/force-push is safe (local only)?

That's it. The commands are easy; the discipline above the commands is the job.
