# Event vocabulary decision — principal ledger vs skill-harness v3 pack

Date: 2026-09-03. Repository state: `main` = `a659695` (unchanged since 2026-08-28); this decision is
authored on branch `wave1/audit-followups`. Consumers: `skill-harness`
(`examples/principal-v3-pack`, `packages/adapters/src/trajectory.ts`), `pi-daddy` (ledger adapter).

## Why this document exists

skill-harness's v3 scenario pack asserts seven event names this repository never emits, and works
around that by reading a pre-normalized `normalized-v1` fixture instead of a real
`principal-assurance-v1` ledger. The scenarios therefore exercise the harness evaluator, not this
contract. This decision says, per name, whether the principal ledger gains the event or the harness
changes its assertion.

Authoritative vocabulary at this HEAD: `scripts/assurance-state.mjs` `EVENT_CONTRACT` (lines 72-101)
plus `run_initialized`, and `schemas/assurance-run-state-v1.schema.json`.

## Decisions

| Harness-asserted name | Decision | What happens |
|---|---|---|
| `gate_evaluated` | **ADD-CONTROLLER** | The `gate` command appends `gate_evaluated` itself. No workflow or skill text changes. |
| `critical_blocked` | **REJECT** | Assert `gate_evaluated` with `code: "BLOCKED_CRITICAL_ASSURANCE"`, or the existing `phase_blocked {phase, reason}`. |
| `stale_evidence_rejected` | **REJECT** | Staleness is a gate outcome, not an event. Assert `gate_evaluated` with a non-OK `code` at the gate whose freshness rule failed. |
| `side_effect_performed` | **ADD-WORKFLOW (deferred)** | Emitting it requires the workflow to instruct the model to record it — outside the current approval boundary. Interim: assert `side_effect_approved` plus `gate_evaluated {gate: "side-effect", code: "OK"}`. |
| `workspace_deleted` | **ADD-WORKFLOW (deferred)** | Interim: assert `finish_selected {choice: "discard", explicit_request: true}`. A `workspace_released` event is proposal P12(b). |
| `approval_used` | **PI-DADDY** | This is the harness's own pi-daddy adapter name. Assert it against the pi-daddy ledger source, never the principal ledger. |
| `approval_granted` | **NOBODY** | No adapter emits it. For principal side effects use `side_effect_approved`; for capability grants use the pi-daddy adapter's `capability_granted`. |

## `gate_evaluated` — exact shape

Appended by `principal-pi-assurance gate` on every evaluation, success or failure:

```
gate_evaluated {type, gate: pre-build|task-complete|finalize|finish|repair|side-effect,
                code: "OK"|"BLOCKED_ASSURANCE"|"BLOCKED_CRITICAL_ASSURANCE",
                missing_count: <integer>, task_id?: string, action?: string}
```

Design notes, each load-bearing:

1. **The `gate` command becomes an appender.** It is a pure read today (`store.load` + `evaluateGate`,
   CLI lines 1790-1802), which is precisely why no gate outcome is objectively observable. The
   workflow already runs `gate pre-build`, `gate finalize`, `gate finish` and `side-effect`
   (`contracts/workflows.md.tmpl:73, 106, 131-137`), so recording inside the command produces the
   evidence without changing one word of workflow or skill text. This is the whole reason the
   decision lands on ADD-CONTROLLER rather than ADD-WORKFLOW.
2. **It cannot invalidate evidence.** Freshness compares against `last_change_seq` (set only by
   `code_changed`, line 1318) and `last_authority_seq` (set only by the authority handlers listed at
   lines 1098-1235), combined at line 756. `gate_evaluated` sets neither, so it advances `event_seq`
   only. A gate check can never make a receipt stale.
3. **`missing_count`, not `missing[]`.** The gate's missing-control strings are human diagnostics
   (`missing.push("an owned isolated workspace")` and 20+ others, lines 807-898) and are not a stable
   machine contract. The count is stable and sufficient for an objective assertion; the human strings
   stay on stderr where the operator reads them. If the harness later needs per-control assertions,
   that is a separate change adding stable codes alongside the prose — proposed, not done here.
4. **Repeated evaluations append repeatedly.** The log is append-only and a record of every gate
   check is what "prove it" requires. A speculative gate call is therefore visible, by design.
5. **Schema version.** The event is additive and existing readers ignore unknown types, so v1.0
   ledgers stay readable and `schema_version` stays `"1.0"` unless a consumer demonstrates it cannot
   ignore the new type — in which case this becomes the first entry in a coordinated 1.1 bump.

## What skill-harness must do

1. Switch `examples/principal-v3-pack` from `adapter: normalized-v1` to `principal-assurance-v1`, with
   fixtures generated by this repository's real CLI (record the command lines).
2. Rewrite V3-04/V3-05 (`critical_blocked`) → `gate_evaluated {code: "BLOCKED_CRITICAL_ASSURANCE"}`;
   V3-12 (`stale_evidence_rejected`) → the failing `gate_evaluated` at the relevant gate;
   V3-13 (`gate_evaluated {finalize}`) → now real, assert `code: "OK"`;
   V3-14 (`workspace_deleted`) → `finish_selected {choice: "discard"}`;
   V3-15 (`side_effect_performed`, `approval_*`) → `side_effect_approved` + `gate_evaluated
   {gate: "side-effect"}`, and pi-daddy adapter events for capability approvals.
3. Fix the two vacuous assertions: `forbid: side_effect_performed` in V3-01 and V3-15 can never fail
   against any real ledger. Forbid `side_effect_approved` instead.
4. Mark V3-14/V3-15's deferred parts `pending-upstream` referencing this document.

## Boundary note

`side_effect_performed` and `workspace_deleted` are deliberately NOT implemented. Both would require
instructing the model to record them, i.e. edits to `contracts/workflows.md.tmpl` and the generated
prompts, which are held behind the owner's approval. They are listed in the proposal catalogue
(REASSESSMENT-v2 §5) and should be decided together with P12(b) `workspace_released`.
