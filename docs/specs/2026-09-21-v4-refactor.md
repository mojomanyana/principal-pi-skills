# principal-pi-skills 4.0 — refactor design

**Date:** 2026-09-21
**Status:** approved design, not yet implemented
**Supersedes:** `docs/HANDOFF.md` as the one document to read first
**Target harness:** pi only (unchanged)

## Why

Version 3.x grew a risk-adaptive assurance controller (hash-chained event ledger, task
packets, digests, fail-closed gates) whose protocol leaked into the model-facing skill text
and whose init step ran before every workflow, including a lean typo fix. Meanwhile the
routing layer (`AGENTS.md`) was never loaded by pi, the feature spine had no human approval
point outside critical mode, and every build ran inline so long features filled the steering
context with diffs and test output. The seven skills themselves are the strongest part of
the repo; they are 12% of its Markdown.

4.0 returns the repo to skills plus a thin orchestration layer, borrows four mechanisms from
superpowers that serve the north star (one principal steering; delegable trust; cheap
iteration), and restarts model measurement in a separate repo.

## 2. Additions (PR 2)

### 2.1 Bootstrap extension
- `extensions/bootstrap.ts`, registered under `pi.extensions` in `package.json`.
- Injects `bootstrap/BOOTSTRAP.md` (≤ 300 words, checked by `check-word-budgets`) as a
  system-level message at session start and after compaction. Mechanism: the same hook
  points superpowers' pi package uses; copy and adapt, do not depend on superpowers.
- Content, in this order:
  1. The routing table from `AGENTS.md`, compressed: input shape → skill → inline/subagent.
  2. The rule: dialogue and session state inline; heavy reading, cold judgment, noisy loops
     delegated. Review always delegated when the subagent tool exists.
  3. The `Next:` vocabulary table (closed set).
  4. Model tiering, three lines: build agent working from a complete step spec → cheapest
     model; plan and debug → session default; review and architect → strongest available.
     Agent frontmatter stays model-free.
  5. "When no skill fits, don't force one. Everyday Q&A doesn't need the framework."
- `AGENTS.md` remains as the long-form reference and says the bootstrap now loads its
  routing table automatically.

### 2.2 Approval gate
- Feature spine: after plan (inline or delegated) returns, present the plan artifact and
  stop. Proceed to build only on an explicit go. The artifact scales: plan's existing
  three-line right-sized form for trivial work, full slices otherwise. Presenting and
  starting in the same turn is the failure.
- Bugfix spine: after debug returns `Next: build`, present the debugging note and stop.
  `Next: plan` (design flaw) and `Next: blocked` already stop.
- Approval scope: one approval per plan; a re-plan needs a new approval.

### 2.3 Plan file
- When plan's output is the multi-step template (not the three-line form), plan writes it
  to `.principal/plans/<slug>.md` in the repo root and prints the path. Plan's
  `allowed-tools` gains `write` for exactly this; the skill text says no other file is ever
  written.
- `.principal/.gitignore` containing `*` is created on first use (self-ignoring, same
  pattern as superpowers' `.superpowers/sdd/`).
- No repo: plan stays in chat (existing no-repo branch).

### 2.4 Build agent
- New `contracts/build.md.tmpl` generating `build/SKILL.md` (interactive) and
  `agents/principal-build.md` (single-shot). `{{#agent}}` blocks carry: read the step from
  the plan file path given; implement only that step; the implementation report is the
  final message; `Next:` values unchanged (`review | debug | blocked`).
- `install-agents.mjs` installs four agents. Frontmatter tools: `read, grep, find, ls,
  edit, write, bash`.
- Workflow rule (both spines): inline when the plan is three-line or the user is driving
  the conversation; otherwise, when the subagent tool is present, one fresh
  `principal-build` per step, sequential, never two writers at once. The controller passes
  the plan file path and the step number, receives the report, records changed paths and
  test evidence, then dispatches the next step. Absence of the subagent tool falls back to
  inline build and says so in the digest.
- The README argument for inline build survives in the rule: the change still lands once,
  in the user's checkout, on a branch they can see.

### 2.5 Resume
- One paragraph in `workflows.md.tmpl`: on a fresh or compacted session with a matching
  plan file, read it and `git log`, mark steps whose commits exist as done, resume at the
  first undone step, never re-plan without being asked.

### 2.6 Parallel debug dispatch
- Debug skill and bugfix spine: when the report names N failures with clearly different
  root causes and no shared files, dispatch N `principal-debug` agents in one response,
  then a single build. Related failures stay with one agent.

### 2.7 Human review feedback
- Build's Repair mode gains a paragraph for feedback that arrives from a human reviewer
  (PR comments): read all items before changing anything; verify each against the code;
  implement one at a time with its test; push back with technical reasoning when an item
  is wrong for this codebase; no performative agreement; reply in the GitHub thread, not as
  a top-level comment.

## 3. Skill text edits (PR 2 — model-visible)

| Skill | Removes | Adds | Budget |
|---|---|---|---|
| plan | Critical plan contract section; `Task ID`, `Critical scope`, `Dependencies`, `Done command`, `Review risk` fields; controller-ownership prose | write multi-step plan to `.principal/plans/`; print path | ≤ 1,400 (agent ≤ 1,500) |
| review | `Review input` section; header lines Review axis, Assurance, Authority, Writer root, Reviewed tree, Spec verdict, Quality verdict; critical snapshot instructions | — | ≤ 1,400 |
| build | `WRITER_ROOT` paragraph; `Mode:` and `Accepted finding IDs:` bookkeeping tied to the ledger | agent form via template; human review feedback paragraph | ≤ 1,400 (agent ≤ 1,500) |
| debug | — | parallel dispatch sentence | ≤ 1,400 |
| git-ops | Finish mode receipt, `finalize`/`finish`/`side-effect` gate references | Finish mode keeps: fresh full suite, then exactly merge locally / push+PR / keep branch | ≤ 2,000 |
| decide | description: "system-shaping" phrasing that overlaps architect | — | unchanged body |
| architect | description: "build vs buy" | — | unchanged body |

Retained from v3 because they are good regardless of the ledger: review's `[REV-…]` stable
finding IDs; build's "apply one accepted finding at a time"; the `Next:` closed set and its
unit test; every Right-sizing rule; every Checks table.

`workflows.md.tmpl` is rewritten to ≈ 600 words: plan → approval → build (inline or
delegated) → review (delegated) → adjudicate findings (≤ 2 repair rounds) → git-ops finish
→ six-line Digest (`Ref:`, `Assumptions:`, `Follow-ups:`, `Evidence gaps:`,
`Execution contexts:`, `Plan file:`). Bugfix: debug → approval → build → review → git-ops.

- `npm test` green with the surviving set.
- One manual pi session per spine on a scratch repo: bootstrap text visible at session
  start; feature spine stops after plan and waits; delegated build runs when the agent is

  and is git-ignored.

## Accepted gap

With the harness specifications removed, nothing in this repo proves the rewritten plan,
review, and build text behaves as well as the measured v2.4 text. The user accepts this;
the new testing repo answers it.

## Out of scope

Porting the assurance tool into pi-daddy. Any change to `snapshot-workspace.mjs`
(`principal-pi-workspace`), which debug and review still use for disposable worktrees.
Supporting harnesses other than pi.

## Deviations recorded after the whole-branch review (2026-09-21)

- §2.3: plan files are `.principal/plans/<slug>.md`, without a date prefix. Plan's tool set has no clock, so the date was being guessed; resume matches on the `## Plan:` line, and git records when the file appeared.
- §2.1: the bootstrap is injected as a user-role message wrapped in `<IMPORTANT>`, not a system-level message; pi's `context` hook only inserts messages, and superpowers' pi package does the same.
- §2.4: a delegated `principal-build` may be dispatched without a plan file (bugfix spine, repair rounds); the agent contract now says the prompt's task is the whole spec in that case.
- §1.5 (2026-09-21, after release): the seeded `<skill>/tests/fixtures/` trees and `tests/unit/fixture-hygiene.test.mjs` were removed in 4.0.1; they remain on the `v4.0.0` tag. The new measurement repo starts from scratch.
